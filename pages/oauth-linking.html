SECURITY LAB 02

OAuth Account Linking Flaw

Learn how insecure account linking can allow an attacker to associate an external identity with another user's account.

OWASP: A07:2021 - Identification and Authentication Failures CWE-287

01. Understanding the Vulnerability

What is OAuth Account Linking?

OAuth account linking allows a user to connect an external identity, such as Google, to an existing application account. A vulnerability occurs when an application accepts an OAuth linking response without ensuring that the person who started the linking process is the same user whose account is being modified.

THE VULNERABILITY SCENARIO

How Does the Attack Happen?

Consider an application where a logged-in user can link an external Google identity to their account.

01

Attacker's Account

The attacker owns an account on the application and controls an external Google identity.

attacker-google-id
02

Start Linking Process

The attacker initiates the OAuth linking process and receives an authorization response for their identity.

OAuth authorization code
03

Victim's Active Session

The victim is signed in to the application. The attacker tricks the victim's browser into submitting the attacker's linking response while the victim's session is active.

victim-session
04

Unauthorized Account Linking

Without validating the OAuth transaction and binding it to the initiating session, the application links the attacker's external identity to the victim's account.

Attacker identity → Victim account
ROOT CAUSE

Why Does This Happen?

The application does not properly verify that the OAuth linking transaction belongs to the same user session that initiated it. Missing or incorrectly validated state and session binding can allow an attacker-controlled authorization response to be associated with another user's active account. A secure implementation must validate a random, single-use state value bound to the initiating session before completing the link.

03. Vulnerable vs Fixed Implementation

Compare an unsafe OAuth callback implementation with a secure approach that validates state and binds the linking transaction to the session that initiated it.

async function oauthCallback(req, session) {
    const code = req.query.code;
    const identity = await exchangeCode(code);

    const user = session.currentUser;

    await linkExternalIdentity(user.id, identity.iss, identity.sub);

AFTER FIX

Fixed Implementation

PROTECTED
account-linking-fixed.js JavaScript 
async function oauthCallback(req, session) {
    const { code, state } = req.query;
    const pending = session.pendingOAuth;

    if (!pending || pending.used || state !== pending.state || pending.userId !== session.userId) {
        throw new Error("Invalid OAuth transaction");
    }

    const identity = await exchangeCode(code, pending.codeVerifier);
    await linkExternalIdentity(pending.userId, identity.iss, identity.sub);
    delete session.pendingOAuth;
    return "Account linked safely";
}

04. Impact

Improper account linking may allow an attacker to associate an external identity with another user's account. Depending on the application's authentication design, this can lead to unauthorized account access, account takeover, and exposure of private information.

05. Security Recommendations

  • Generate a cryptographically random state value for every OAuth linking transaction.
  • Store the expected state value in the session that initiated the linking process.
  • Validate the returned state against the pending transaction before accepting the OAuth callback.
  • Reject callbacks with missing, invalid, expired, or previously used state values.
  • Bind every pending linking transaction to the authenticated user who initiated it.
  • Require explicit account-owner authorization before associating an external identity.
  • Use PKCE (S256) where supported to protect authorization-code redemption.
  • Validate the identity response, including signature, issuer, audience, and expiration.
